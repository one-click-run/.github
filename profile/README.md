# One-Click-Run 组织

## 组织简介

**One-Click-Run** 是一个专注于提供可长期使用、可复现且易于运行的开源工具环境的组织。

我们希望降低开源软件的配置和使用门槛，但相比“安装得快”，我们更看重“在未来仍然可以使用”。

因此，我们不仅提供一键运行和部署脚本，也会在必要时保存经过验证的安装资源、依赖文件及预构建便携包，尽量避免因为上游仓库变动、依赖下线或网络环境变化而导致项目失效。

我们的目标是：

> 让一个今天可以运行的开源工具，在未来尽可能仍然可以被验证、获取、部署和运行。

项目将优先支持原生、便携的运行方式，并逐步扩展到 Windows、Linux、macOS 等平台。对于无法直接在目标平台运行的软件，也可能提供容器或其他兼容方案。

## 我们的理念

### 可用性优先

一个完全透明、但已经无法下载依赖或无法运行的脚本，并没有太大的实际价值。

我们会优先保证发布版本能够真正运行。为此，项目可能会：

- 锁定经过验证的工具和依赖版本；
- 保存构建所需的关键资源；
- 在本组织的 Release 中重新托管容易失效的依赖；
- 提供经过完整测试的预构建包或便携环境；
- 保留较旧但稳定的版本，而不是盲目追逐最新版本。

我们不承诺始终提供最新版本，但会尽量确保已经发布的版本保持可用。

### 透明可审计

提供二进制文件并不意味着放弃透明性。

当项目分发预构建包时，我们会尽可能同时提供：

- 构建和组装脚本；
- 精确的上游版本、提交或标签；
- 依赖来源和下载地址；
- 必要的补丁及其用途；
- 文件校验值；
- 自动构建和测试记录；
- 软件物料清单（SBOM）；
- 第三方软件及许可证说明；
- 可供维护者复现构建过程的文档。

用户应当能够知道压缩包中包含什么、这些文件来自哪里，以及它们是如何被生成的。

受上游环境、时间戳、压缩工具和构建平台影响，我们不一定能保证不同机器生成的文件逐字节相同，但会尽量保证构建过程公开、来源明确且结果可验证。

### 关键资源自托管

仅仅锁定版本并不能保证长期可用。上游仓库、Release、包管理器或下载地址都可能发生变化或消失。

对于维持已发布环境运行所必需的关键文件，我们会在许可证允许的范围内保存副本，并通过本组织控制的发布渠道进行托管。

运行已发布环境时，应尽量只依赖本组织提供的文件，而不再临时访问上游服务。

重新构建环境的脚本仍可能依赖外部网络和上游源码。由于外部环境会变化，我们无法保证复现脚本永久有效，但会记录当时有效的完整来源和构建过程。

### 便携与隔离

项目优先采用自包含、可移动的运行方式，并尽量避免对系统环境造成永久修改。

便携环境通常应当具备以下特征：

- 不永久修改系统 `PATH` 或其他全局环境变量；
- 不强制将依赖安装到系统目录；
- 配置、缓存和用户数据尽量保存在项目自身目录；
- 可以复制、移动或改名；
- 不再需要时可以通过删除目录完成清理；
- 不干扰系统中已有的同类工具或用户配置。

如果某个工具确实需要驱动、容器运行时、系统组件或其他无法便携封装的依赖，项目会明确说明这些前置条件。

### 依赖锁定与版本稳定

我们会锁定上游工具、源码和依赖的具体版本，避免未经验证的自动升级破坏现有环境。

发布后的运行环境不应在用户不知情的情况下：

- 自动更新工具；
- 下载新的编译器或运行时；
- 替换已经锁定的依赖；
- 修改全局软件或系统配置。

用户主动安装额外依赖或升级组件的行为，不属于原始发布环境的离线与稳定性承诺范围。

### 自动验证

一个压缩包能够成功生成，并不代表它真正可用。

项目应尽可能通过自动化测试验证完整的用户流程，包括：

1. 获取发布文件；
2. 校验文件完整性；
3. 解压或安装到干净目录；
4. 在隔离或断网条件下启动环境；
5. 编译或运行示例程序；
6. 验证语言服务器、编辑器插件或其他配套功能；
7. 验证目录移动后仍能正常使用。

### 跨平台与兼容方案

One-Click-Run 不再局限于 Windows。

不同项目可以根据上游软件的实际支持情况提供：

- Windows 原生环境；
- Linux 原生环境；
- macOS 原生环境；
- Docker 或其他容器环境；
- 虚拟机、兼容层或平台特定方案。

我们不会为了形式上的统一，强迫所有平台使用同一种实现方式。每个仓库应明确列出它实际支持和测试过的平台。

### 开源与权利归属

本组织只收录允许公开使用和分发的开源软件及相关资源，不将第三方软件宣称为本组织所有。

仓库中的启动器、构建脚本和补丁使用仓库声明的许可证。便携包、预构建工具及其中包含的第三方文件，继续遵循各自上游项目的许可证和权利声明。

如果上游许可证不允许重新分发某些文件，我们将只提供获取或构建脚本，并明确说明相应限制。

## 组织结构

除特殊说明外，每个仓库对应一个独立工具、项目或开发环境。

仓库会根据目标平台提供一个或多个清晰的启动入口，例如：

- Windows：`run.cmd`、`run.ps1` 或生成的启动器；
- Linux/macOS：`run.sh` 或对应的原生入口；
- 容器环境：Docker Compose 或经过封装的启动脚本。

不同项目的具体使用方式、支持平台、离线范围和前置条件，以各仓库的 README 和发布说明为准。

## 发布内容

根据项目特点，一个仓库可能提供以下一种或多种内容：

- 一键部署脚本；
- 便携运行环境；
- 预构建二进制文件；
- 自托管的固定版本依赖；
- 容器镜像或容器配置；
- 构建与复现脚本；
- 来源清单、校验文件和 SBOM；
- 自动化测试和发布记录。

是否提供二进制文件取决于可用性、构建成本、许可证和平台条件，而不是一概排斥二进制分发。

## 常见问题

### 为什么会提供二进制包？

某些工具需要大型编译环境、漫长的构建过程，或者依赖可能随时间失效的上游文件。如果只提供安装脚本，用户仍可能因为网络、上游变动或依赖下线而无法使用。

因此，在许可证允许的情况下，我们会提供经过验证的预构建包，以提高环境的长期可用性。

同时，我们会尽可能公开构建脚本、来源信息、校验值和自动构建记录，避免让预构建包成为无法解释的黑盒。

### 预构建包是否安全？

任何二进制文件都需要建立可信来源，而不能仅凭名称判断安全。

我们会通过来源锁定、公开构建脚本、文件校验值、自动构建记录、依赖清单和复现文档，让用户能够检查发布内容的来源与生成过程。

用户仍应根据自己的安全要求审查脚本、校验文件并决定是否使用。

### 为什么不始终使用最新版本？

最新版本不一定是最稳定或最容易长期保存的版本。

我们更重视已经验证的组合是否可以持续运行。项目可能长期保留某个稳定版本，只有在新版本完成构建、兼容性和离线测试后才进行升级。

### 发布包是否完全离线？

这取决于具体项目。

仓库会明确说明：

- 哪些功能可以完全离线使用；
- 哪些文件由本组织托管；
- 哪些操作仍会访问网络；
- 用户安装额外依赖时可能联系哪些外部服务。

已经承诺离线运行的核心功能，不应在启动时临时下载组件。

### 如果上游项目消失了怎么办？

如果许可证允许，并且关键源码或发布文件已经被本组织保存，那么现有发布版本仍应能够继续安装或运行。

重新构建可能仍受到编译工具、操作系统和外部生态变化的影响，因此我们会尽量保存来源、补丁、依赖和构建记录，但无法保证任何构建流程永久不受外部变化影响。

### 如果工具不支持某个平台怎么办？

我们会根据实际情况选择容器、兼容层、虚拟机或其他替代方案。

如果无法提供可靠方案，仓库会明确标注不支持的平台，而不会声称未经验证的兼容性。

### 便携环境真的不会影响系统吗？

我们的目标是尽量避免永久修改系统配置，并将工具、配置、缓存和用户数据保存在项目目录内。

但显卡驱动、Docker、系统运行库、安全软件和操作系统组件等外部条件无法完全封装。每个仓库会列出已知的系统要求和可能产生的影响。
